# Bundle Conventions

The audit's output is an **analysis bundle** — a folder of small markdown files, not one
document — because not every reader needs all the information at once. This file is the
single source of truth for the bundle's layout, frontmatter, index rules, writing style,
and audience-document templates. It is *inspired by* the Open Knowledge Format (OKF) — a
directory of markdown files with YAML frontmatter, cross-linked with bundle-relative links —
but makes no claim to be OKF-conformant: this is single-run audit state, not a shared
knowledge base. We borrow the shape (`type` frontmatter, per-concept files, relative links,
a regenerable `index.md`) and add our own keys freely.

## Two axes

- **Vertical slices = the ten dimensions.** Each dimension is a self-contained folder under
  `dimensions/`, with a full `detail.md` and a bounded `summary.md`. Read one concern top to
  bottom without wading through the rest.
- **Horizontal slices = layers that cut across all dimensions.** Depth: `index.md` →
  per-dimension `summary.md` → `scorecard.md` → per-dimension `detail.md`. Audience:
  `docs/doc-executive.md`, `doc-business.md`, `doc-technical.md`, each synthesizing across
  all ten dimensions for one reader and one decision.

## Folder layout

```
{{AUDIT_FOLDER}}/
├── index.md                         # type: Index — regenerable listing, grouped by type, no live state
├── STATE.md                         # type: State — live workflow state (single source), never regenerated
├── log.md                           # type: Log — verbatim prompts + stage timeline (optional but recommended)
├── recon.md                         # type: Recon — orientation pass; shared context for dimension scoring
├── scorecard.md                     # type: Scorecard — MACHINE-GENERATED by build_scorecard.py; never hand-edit
├── dimensions/
│   └── <dimension>/                 # one folder per dimension (VERTICAL slice)
│       ├── result.json              # machine record consumed by the scorer (schema in SKILL.md)
│       ├── detail.md                # type: Dimension — full evidence, findings, recommendations
│       └── summary.md               # type: Summary — bounded: level, gate/pressure role, top finding
├── docs/                            # audience seeds (HORIZONTAL slices) — generated only after the review gate
│   ├── doc-technical.md             # type: Doc, audience: technical
│   ├── doc-executive.md             # type: Doc, audience: executive
│   └── doc-business.md              # type: Doc, audience: business
└── adrs/                            # optional — decisions taken during the audit, one file each, append-only
    └── YYYY-MM-DD-<slug>.md
```

Within a dimension folder, `detail.md` sorts before `summary.md` (d < s), so full content
lists first and the compact summary last.

## Frontmatter

Every markdown bundle file carries YAML frontmatter. `type` is the one always-required key;
the rest are workflow extensions.

```yaml
# index.md      -> type: Index
# STATE.md      -> type: State
# log.md        -> type: Log
# recon.md      -> type: Recon, description: <one line>
# scorecard.md  -> type: Scorecard  (written by the script — do not hand-edit)
```

**`dimensions/<dim>/detail.md`:**
```yaml
---
type: Dimension
dimension: security
level: 2
confidence: medium          # high | medium | low
critical: true              # security | testing | reliability -> true
cluster: false              # architecture | performance-scalability | dependency-health | code-quality -> true
description: <one-line statement of the dimension's finding>
---
```

**`dimensions/<dim>/summary.md`:**
```yaml
---
type: Summary
dimension: security
level: 2
detail_file: ./detail.md
description: <one-line outcome>
---
```

**`docs/doc-*.md`** (audience seeds — STE-styled, always `expandable: true`):
```yaml
---
type: Doc
audience: executive         # executive | business | technical
expandable: true
status: COMPLETE
description: <one-line summary for this audience>
---
```

**`adrs/YYYY-MM-DD-<slug>.md`:** `type: ADR`, `status: DECIDED|PENDING`, `date:`, `description:`.

## Navigation bar

`detail.md` and `summary.md` carry a nav bar directly under the H1, so a reader deep in a
long file can get back out:

```markdown
<a id="top"></a>
# <Dimension> — Detail

[Index](../../index.md) · [State](../../STATE.md) · [Scorecard](../../scorecard.md)

---
```

`doc-*.md` and `adrs/*.md` carry **no** nav bar: they are expanded/redacted for external
audiences (docs) or promoted to project stores (ADRs), where bundle-relative links break.

## Stable anchors

`detail.md` emits explicit HTML anchors (never rely on auto-slugged headings) so summaries
and audience docs can deep-link reliably: `<a id="top"></a>`, `<a id="evidence"></a>`,
`<a id="findings"></a>`, `<a id="recommendations"></a>`. Links are always bundle-relative
(`./detail.md#findings`, `../security/detail.md#evidence`) so the folder stays portable when
moved or zipped.

## index.md — regenerable, grouped by type

`index.md` holds links and descriptions only — never live state (that is `STATE.md`'s job).
Rebuild it from the frontmatter of all bundle files whenever the bundle changes. Group by
type, never a flat list, in this order:

1. **Bundle Control** — `recon.md`, `STATE.md`, `log.md`.
2. **Scorecard** — `scorecard.md`.
3. **Dimensions** — one row-pair per dimension, ordered by `level` ascending (lowest first —
   attention most needed at the top), then name. List `detail.md` then `summary.md`.
4. **Audience Documents** — `doc-executive.md`, `doc-business.md`, `doc-technical.md`.
5. **Architecture Decision Records** — `adrs/*.md`, date order, if any.

Omit an empty section. Never emit placeholder rows.

## STATE.md template

```markdown
---
type: State
---

# Audit State

| Field | Value |
|---|---|
| Stage | RECON | SCORING | AWAITING ARCHITECT REVIEW | SYNTHESIS | COMPLETE |
| Dimensions scored | N / 10 |
| Awaiting | none | architect review of scores | corrections |
| Last Updated | YYYY-MM-DD |
```

The review gate lives here: after scoring, set `Stage: AWAITING ARCHITECT REVIEW` and stop.
Only an explicit Architect go-signal moves it to `SYNTHESIS`.

## Dimension templates

**`detail.md`** (analytical register — nuance and hedging allowed; NOT STE):
```markdown
---
type: Dimension
dimension: <name>
level: <0-4>
confidence: <high|medium|low>
critical: <true|false>
cluster: <true|false>
description: <one line>
---

<a id="top"></a>
# <Dimension> — Detail

[Index](../../index.md) · [State](../../STATE.md) · [Scorecard](../../scorecard.md)

---

**Level <N> (<Label>) · confidence <…>** — <one-sentence justification, calibrated to the software type>

<a id="evidence"></a>
## Evidence
- <observation> — `<path>`

<a id="findings"></a>
## Findings
- **[<severity>]** <summary> — <detail>

<a id="recommendations"></a>
## Recommendations
- **[<priority>]** <action> — <rationale>
```

**`summary.md`** (bounded — stays small no matter how large `detail.md` grows):
```markdown
---
type: Summary
dimension: <name>
level: <0-4>
detail_file: ./detail.md
description: <one-line outcome>
---

<a id="top"></a>
# <Dimension> — Summary

[Index](../../index.md) · [State](../../STATE.md) · [Scorecard](../../scorecard.md)

---

**Level <N> (<Label>) · confidence <…>**

- **Role:** <critical/gate contribution and/or modernization-cluster contribution>
- **Top finding:** <the one thing that matters most> → [detail](./detail.md#findings)
- **First move:** <the highest-leverage recommendation> → [detail](./detail.md#recommendations)
```

## Audience documents (horizontal seeds)

All three are **expansion seeds, not finished documents**: terse bullets under fixed
headings, `expandable: true`, written in STE style (below), and never shared verbatim
outside the team — an external reader always receives a redacted and/or expanded version
generated from the seed. Generate them **only after the review gate**.

### `doc-technical.md` — development team
```markdown
# <Application> — Technical Audit Record (seed)

## Verdict
- Overall Level <X.X>; readiness gate Level <N> (<dims>); modernization pressure <High/Med/Low>.

## Scorecard
- See [scorecard](../scorecard.md). Dimensions, lowest level first: <list with links to each detail.md>.

## Key findings (by dimension, weakest first)
- **<dimension>** — [<severity>] <finding> → [detail](../dimensions/<dim>/detail.md#findings)

## Prioritized roadmap
- **Quick wins:** <action> (<dimension>)
- **Next:** <action> (<dimension>)
- **Strategic:** <action> (<dimension>)

## TCO & System Profile
- Composition (from recon): <decomposition style, tiers, coupling, data arch>.
- TCO signature <High/Moderate/Low> (relative); heaviest driver **adaptability** — resistance hotspots: <modules with large ripple radius>.

## Methodology & limitations
- Static (code-only) audit; performance inferred, not measured. <what would need profiling>.
```

### `doc-business.md` — business stakeholder
```markdown
# <Application> — Business Impact (seed)

## The four symptoms, in plain terms
- **Slow:** <plain-language status>.
- **Insecure:** <…>.
- **Hard to maintain:** <…>.
- **Outdated architecture:** <…>.

## What This Costs Today
- <velocity drag, risk exposure, scaling ceiling — in business terms, each tied to a symptom>.

## What "Future-Proof" Unlocks
- <what becomes possible once the weak areas are addressed>.

## Not Included
- <explicit boundaries — this is an assessment, not a delivery plan>.
```

### `doc-executive.md` — executive / sponsor  (EVOLUTION-GAP DISCIPLINE)
This is the fund-the-work document. It exists so a budget owner can defend spend on
**concrete, evidenced gaps** — never on a vague "the system is old / should be modernized"
line item. Every claim ties to a specific dimension finding. State the gap and its business
consequence only; **no invented solution, timeline, or cost** — those are not the audit's job.
```markdown
# <Application> — Maturity Verdict (seed)

> Assessment, not a delivery plan. Every gap below is evidenced in a dimension detail file.
> Cost and timeline are out of scope for this brief.

## Verdict
- Can it keep running as-is? Readiness gate: Level <N> — <one sentence>.
- How urgent is modernization? Pressure: <High/Med/Low>, driven by <drivers>.

## What Is Weak Today (evidenced)
- <dimension>: <the concrete gap> — basis: `<path or finding>` → [detail](../dimensions/<dim>/detail.md#findings)

## Business Consequence
- <what each weak area costs or prevents if left unaddressed — in budget-owner terms>.

## Cost of Ownership (relative)
- System shape (from recon System Profile): <one line>.
- TCO signature: <High/Moderate/Low>, driven by <drivers>. **Adaptability** is the largest driver — <hotspot>: roadmap items touching it will tend to run over their estimates, predictably in one direction. Discount budget/timeline confidence there.
- Relative signature only; monetary figures are out of scope.

## Scope Note
- Static assessment. Solution, cost, and timeline are deliberately out of scope.
```

## STE-style writing (for `doc-*.md` only)

The audience documents use the *style* of Simplified Technical English (ASD-STE100) — a
controlled, unambiguous, translation-friendly register. STE-styled, not certified.

1. Short sentences — one idea each (≤ ~20 words procedural, ≤ ~25 descriptive).
2. Active voice. 3. Imperative for instructions. 4. One meaning per word; don't reuse a word
as both noun and verb. 5. No noun clusters over three words. 6. Simple tenses. 7. One topic
per paragraph, kept short. 8. Consistent terminology — same word for the same thing every
time; reuse the application's own domain terms. 9. Plain vocabulary ("use" not "utilise").
10. No ambiguous pronouns — repeat the noun.

STE applies **only** to `doc-*.md`. It does **not** apply to `detail.md`, `summary.md`,
`recon.md`, `scorecard.md`, `STATE.md`, or `log.md` — analytical writing needs the nuance
STE removes, and the log is verbatim.

## Bundle rules (invariants)

- **`scorecard.md` is machine-owned** — always regenerated by `build_scorecard.py`, never
  hand-edited. The three signals come from the script, not from prose.
- **Every level traces to a path.** A score with no cited evidence is not a valid score.
- **`STATE.md` is the single source of live state**; `index.md` is regenerable and holds no
  live state.
- **The review gate is absolute.** No audience document is written before the Architect has
  reviewed the scores and given an explicit go-signal.
- **ADRs, if used, are append-only** — one file each, never overwritten or deleted.
- **Audience docs are seeds** — never shared verbatim externally; always expanded/redacted
  from the seed for the actual reader.
